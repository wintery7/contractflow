# 01. 문제 정의 · 사용자 시나리오 · MVP 범위

> 상태: M0 초안 (2026-10-16) · 검토 후 확정

## 1. 문제 정의

계약 담당자는 계약서를 받으면 다음 작업을 수작업으로 반복한다.

1. 기간·금액·당사자·갱신·해지·위약금 조항을 찾아 엑셀/메일에 옮겨 적는다.
2. "중도 해지 조건이 뭐였지?" 같은 질문이 생길 때마다 수십 페이지를 다시 읽는다.
3. 검토가 필요한 항목(불리한 위약금, 자동 갱신 통지 기한 등)을 별도로 메모하고 담당자에게 넘긴다.
4. 누가 언제 무엇을 처리했는지 추적하기 어렵다.

**핵심 문제**: 비정형 문서 속 정보를 *구조화된 데이터*와 *추적 가능한 업무*로 바꾸는 과정이 느리고, 결과의 근거를 확인하기 어렵다.

**ContractFlow AI가 해결하는 것**: 계약서 PDF → (1) 근거 페이지가 붙은 구조화 정보, (2) 근거 인용이 포함된 질의응답, (3) 사람이 승인한 검토 업무와 이력.

**해결하지 않는 것 (명시)**
- 법률 자문. 모든 분석 결과는 *검토 보조 자료*이며 응답에 면책 문구를 포함한다.
- 스캔 PDF OCR (MVP 제외, 확장 경로만 설계).
- 다중 사용자 권한 관리 (MVP는 인증 없는 단일 사용자 로컬 데모. 이 사실을 README에 명시).

## 2. 핵심 사용자 시나리오

페르소나: 중소기업 구매/법무 지원 담당자 1인.

| # | 시나리오 | 성공 조건 |
|---|---|---|
| S1 | 계약서 PDF를 업로드한다 | 형식·크기 검증 후 `UPLOADED` 상태 문서가 생성된다 |
| S2 | 분석을 요청하고 진행 상태를 조회한다 | 즉시 `202`와 분석 ID를 받고, 폴링으로 `SUCCEEDED/FAILED`를 확인한다 |
| S3 | 구조화 분석 결과를 확인한다 | 각 필드에 값·상태·근거 인용·페이지·검증 여부가 있고, 문서에 없는 값은 `NOT_FOUND`다 |
| S4 | "중도 해지 조건은?"이라고 질문한다 | 근거 청크·페이지가 붙은 답변을 받는다. 근거가 없으면 `INSUFFICIENT_EVIDENCE`를 받는다 |
| S5 | AI가 제안한 검토 항목 중 하나를 업무로 등록한다 | 사용자가 명시적으로 생성해야 Task가 된다. 같은 제안은 두 번 등록되지 않는다 |
| S6 | 업무의 담당자·상태를 바꾸고 완료 처리한다 | 허용된 상태 전이만 가능하며 변경 이력이 남는다 |
| S7 | 문서의 처리 이력을 조회한다 | 업로드→분석→업무 생성→상태 변경이 시간순으로 보인다 (원문은 저장하지 않음) |
| S8 | 문서를 삭제한다 | 이후 조회·검색이 불가하며 원본 파일과 청크/임베딩이 함께 제거된다 |

## 3. MVP 범위

### MVP (6주 안에 반드시 완성)

| 영역 | 기능 |
|---|---|
| 문서 | 업로드(PDF, 크기·매직바이트 검증, SHA-256 중복 감지), 목록(필터·페이지네이션), 상세, 소프트 삭제 + 콘텐츠 정리 |
| 추출 | 페이지별 텍스트 추출, 정제, 빈 문서/스캔 의심 감지 (`NO_TEXT_LAYER`) |
| 분석 | 비동기 분석 실행(DB 상태 + 백그라운드 실행), 단계(stage) 추적, 중복 실행 방지, 재실행 시 이전 결과 보존 |
| 구조화 추출 | 10개 필드 Pydantic 스키마, 필드별 근거 인용·페이지, **인용문 원문 대조 검증**, 잘못된 JSON 1회 교정 재시도 |
| RAG | 페이지 보존 청킹, 임베딩, pgvector 저장, 문서 범위 검색, 근거 기반 답변, 근거 부족 시 답변 거부 |
| 업무 | Task CRUD, 상태 전이 규칙, 낙관적 잠금(version), AI 제안 → 사용자 승인 흐름 |
| 이력 | 감사 이벤트(행위·대상·시각·결과·변경 필드), LLM 호출 메타데이터 로그 |
| 품질 | 단위/통합/RAG 테스트(Fake LLM), 30+ 문항 평가셋, Recall@k·MRR, 청크 크기/오버랩/top-k 실험 |
| 운영 | Docker Compose, 환경변수 설정, JSON 구조화 로그 + request_id, 헬스체크 |

### 후순위 (시간이 남으면, 우선순위 순)

1. 키워드(BM25) 검색 비교 → 하이브리드 검색 (평가 결과 근거가 있을 때만)
2. Reranking (평가에서 순위 품질 문제가 확인될 때만)
3. 분석 워커 프로세스 분리 (`SELECT … FOR UPDATE SKIP LOCKED` 기반, Redis 없이)
4. API Key 인증 + 문서 소유자(owner_id) 기반 접근 제어
5. 계약 만료 임박 조회 (end_date를 JSONB에서 컬럼으로 승격)
6. 간단한 프런트엔드

### 명시적 제외

OCR, 다중 테넌트, 외부 알림(메일/슬랙), Celery/Redis, MSA, 여러 VectorDB 병행.

## 4. 비기능 요구사항 (MVP 목표)

| 항목 | 목표 | 비고 |
|---|---|---|
| 업로드 최대 크기 | 20 MB | 환경변수로 조정 |
| 최대 페이지 | 100페이지 | 초과 시 `DOCUMENT_TOO_LARGE` |
| 질의응답 지연 | 측정 후 기록 | 목표치를 미리 정하지 않고 M5에서 p50/p95 실측 |
| 민감정보 | 로그에 원문·질문 원문·API 키 미기록 | 길이/해시만 기록 |
| 외부 API | 타임아웃 + 제한적 재시도 | 4xx(검증 오류)는 재시도하지 않음 |
