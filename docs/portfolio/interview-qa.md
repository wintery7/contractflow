# 기술 면접 예상 질문과 답변

각 답변은 "무엇을 했는가 → 왜 → 한계/대안" 순서로 30초~1분 분량을 목표로 한다. 근거 코드 위치를 함께 적었다.

## 아키텍처

**Q1. 전체 구조를 설명해 주세요.**
FastAPI 모듈형 모놀리스 하나와 PostgreSQL(pgvector) 하나로 구성했습니다. 라우터는 HTTP 변환만, 서비스는 유스케이스와 트랜잭션 경계, 도메인은 상태 머신 같은 순수 규칙을 담당합니다. LLM·임베딩·파일 저장소는 프로토콜 뒤에 두고 의존성 주입으로 교체할 수 있어서 테스트에서는 Fake 구현을 씁니다. MSA는 이 규모에서 운영 복잡도만 늘린다고 판단했습니다. (`app/api`, `app/services`, `app/domain`, `app/llm`)

**Q2. 서비스 계층이 HTTP를 모르게 한 이유는?**
같은 서비스 코드를 백그라운드 분석 실행기와 운영 스크립트(고아 파일 정리)에서도 쓰기 때문입니다. 서비스는 `ConflictError` 같은 도메인 예외만 던지고, HTTP 상태 코드로의 변환은 한 곳(`STATUS_BY_ERROR`)에서 합니다. 덕분에 오류 응답 형식도 전체 API에서 하나로 통일됩니다. (`app/api/error_handlers.py`)

## 데이터베이스

**Q3. 중복 업로드·중복 분석을 어떻게 막았나요?**
애플리케이션의 SELECT 확인은 빠른 경로일 뿐이고, 최종 보장은 DB 부분 유니크 인덱스가 합니다. 같은 요청 두 개가 동시에 SELECT를 통과해도 인덱스가 하나만 통과시키고, 다른 하나는 `IntegrityError`를 409로 바꿉니다. 진행 중 분석은 `WHERE status IN ('QUEUED','RUNNING')`, 같은 AI 제안의 중복 승인은 `(source_analysis_id, source_item_id)`에 부분 유니크 인덱스를 걸었습니다.

**Q4. 분석 결과를 JSONB로 저장한 이유는?**
추출 필드 구성이 프롬프트 버전과 함께 바뀌고 항상 통째로 읽기 때문입니다. 필드 단위 조회(예: 만료 임박 계약 목록)가 필요해지면 그 필드만 컬럼으로 승격하는 것이 맞다고 봤습니다.

**Q5. 상태 값에 PostgreSQL ENUM 대신 VARCHAR + CHECK를 쓴 이유는?**
ENUM은 값 추가·삭제 마이그레이션이 번거롭습니다. CHECK 제약으로 같은 무결성을 보장하면서 변경은 쉽게 했습니다.

**Q6. `now()`와 `clock_timestamp()`의 차이를 겪은 적이 있나요?**
네. `now()`는 트랜잭션 시작 시각이라 한 트랜잭션 안에서 만든 행의 시각이 같아집니다. 테스트에서 "최신 분석"이 무작위로 바뀌는 문제로 발견했고, 최신 판단에 쓰는 분석·업무 테이블은 실제 삽입 시각인 `clock_timestamp()`로 바꿨습니다. (`docs/portfolio/troubleshooting.md` 2번)

**Q7. 동시 수정은 어떻게 처리했나요?**
업무(Task)에 `version` 컬럼을 둔 낙관적 잠금입니다. 수정 요청은 마지막으로 읽은 version을 보내고, `UPDATE … WHERE id=? AND version=?`의 영향 행이 0이면 409를 돌려줍니다. 행 잠금을 오래 잡지 않아 대기가 없고, 바뀐 값이 없으면 version을 올리지 않아 재시도가 충돌을 만들지 않습니다. (`app/services/task_service.py`)

## 비동기 처리

**Q8. 분석을 비동기로 처리한 방식과 한계는?**
요청은 분석 행을 QUEUED로 만들고 202를 바로 돌려줍니다. 실행은 FastAPI BackgroundTasks가 응답 후 같은 프로세스에서 하고, 상태의 정본은 DB입니다. 한계는 프로세스가 재시작되면 실행 중이던 작업이 사라진다는 점입니다. 그래서 하트비트가 오래 끊긴 분석은 앱 시작 시 INTERRUPTED로 정리하고, 자동 재실행은 중복 비용 때문에 하지 않습니다. 다중 서버로 가면 같은 테이블을 `SELECT … FOR UPDATE SKIP LOCKED`로 가져가는 워커로 바꾸면 되고, Celery·Redis는 그 이후의 선택지입니다.

**Q9. 같은 분석이 두 번 실행되지 않게 한 방법은?**
세 겹입니다. 문서 행 잠금으로 요청을 줄 세우고, 부분 유니크 인덱스로 진행 중 분석을 하나로 제한하고, 실행기는 상태가 QUEUED가 아니면 아무것도 하지 않습니다. 또 같은 파이프라인·모델·프롬프트로 성공한 결과가 있으면 LLM을 다시 부르지 않고 재사용합니다.

## LLM·RAG

**Q10. LLM 출력이 잘못된 JSON일 때는?**
OpenAI strict JSON 스키마로 형식 오류 자체를 줄이고, 응답은 서버에서 Pydantic으로 반드시 다시 검증합니다. 실패하면 어느 필드가 왜 틀렸는지 알려 주고 한 번만 교정을 요청하고, 두 번 실패하면 분석을 `LLM_INVALID_OUTPUT`으로 끝냅니다. 네트워크·429·5xx 재시도는 SDK의 지수 백오프에 맡겨 재시도가 겹치지 않게 했습니다. (`app/llm/structured.py`)

**Q11. 환각을 어떻게 다뤘나요?**
세 가지입니다. ① 스키마 단계에서 "NOT_FOUND인데 값이 있음", "FOUND인데 근거가 없음" 같은 응답을 거절합니다. ② 모든 근거 인용문을 서버가 원문 페이지와 대조해 VERIFIED/UNVERIFIED를 표시합니다. ③ 질의응답에서는 실제로 넘긴 청크를 인용하지 않은 답은 돌려주지 않습니다. LLM이 스스로 매기는 신뢰도 점수는 근거가 없어서 쓰지 않았습니다.

**Q12. VERIFIED면 추출 값이 정확한 건가요?**
아닙니다. 인용문이 원문에 존재한다는 뜻일 뿐, 그 인용으로부터 뽑은 값이 맞는지는 별개입니다. 값의 정확도는 평가셋으로 따로 측정해야 합니다.

**Q13. 벡터 DB로 pgvector를 고른 이유는?**
문서를 지울 때 청크와 벡터를 같은 트랜잭션에서 지울 수 있어 고아 벡터가 생기지 않고, 구성 요소도 하나 줄어듭니다. 그리고 질문은 항상 한 문서 범위라 ANN 인덱스 없이 문서 ID로 범위를 좁힌 뒤 정확한 코사인 거리를 계산합니다. HNSW에 문서 필터를 걸면 탐색 후 필터링 때문에 결과가 k개보다 적게 나올 수 있다는 점도 고려했습니다.

**Q14. 유사도 점수가 높으면 답이 맞다고 볼 수 있나요?**
아닙니다. 유사도는 주제가 비슷하다는 신호입니다. 예를 들어 "해지"와 "해제", "지체상금"과 "손해배상"은 점수가 비슷하게 나올 수 있습니다. 그래서 검색 단계 임계값은 명백히 관련 없는 질문만 거르는 용도로 쓰고, 답의 근거 일치는 인용 검증과 평가셋으로 따로 봅니다.

**Q15. 청킹 전략은?**
조항 경계("제N조")에서 새 청크를 시작하고, 크기 제한을 넘으면 문장 단위, 그래도 길면 글자 수로 자릅니다. 겹침을 둬서 경계에 걸친 문장이 끊기지 않게 하고, 청크마다 페이지 범위를 보존해 답의 출처 페이지를 보여 줍니다. 크기와 겹침 값은 평가셋으로 정합니다.

**Q16. 프롬프트 인젝션은 어떻게 막았나요?**
문서와 질문을 구획 태그 안에만 넣고 그 안의 지시를 따르지 말라고 시스템 프롬프트에 명시했습니다. 문서가 `</document>` 같은 문자열로 구획을 탈출하지 못하게 태그를 다른 문자로 바꾸고, 출력은 스키마로 제한하며, 모델에는 도구 실행 권한이 없습니다. 가장 중요한 것은 AI 결과가 사람 승인 없이 어떤 상태도 바꾸지 않는다는 점입니다. 업무 생성은 사용자 요청으로만 됩니다. 완전히 막을 수는 없으므로 피해 범위를 줄이는 설계로 봤습니다.

## 테스트·운영

**Q17. 외부 LLM에 의존하는 코드를 어떻게 테스트했나요?**
`LLMClient`·`Embedder` 프로토콜 뒤에 Fake 구현을 두고 응답·예외를 주입합니다. 잘못된 JSON, 타임아웃, 근거 없는 인용 같은 실패 시나리오를 결정적으로 재현할 수 있습니다. 실제 API 호출 테스트는 `-m live`로 분리해 CI에서 비용·네트워크 때문에 흔들리지 않게 했습니다.

**Q18. 통합 테스트의 DB 격리는?**
테스트마다 바깥 트랜잭션을 열고, 서비스의 commit은 SAVEPOINT로만 반영되게 한 뒤 끝나면 롤백합니다. 서비스 코드는 운영과 똑같이 commit을 호출합니다. 세션은 요청마다 새로 열어 운영과 같은 조건을 만들었고, 스키마는 Alembic으로 만들어 마이그레이션 자체도 함께 검증합니다. 다른 DB를 지우지 않도록 DB 이름이 `_test`로 끝나지 않으면 실행을 거부합니다.

**Q19. 로그에서 민감정보는?**
계약서 원문, 질문·답변 본문, API 키는 기록하지 않고 ID·길이·지연·오류 코드만 남깁니다. 포매터에서 `sk-` 패턴을 마스킹하고, 요청 ID를 백그라운드 작업까지 이어 붙여 한 요청의 흐름을 추적합니다. LLM 호출은 토큰·지연·상태만 `llm_calls` 테이블에 남겨 비용과 실패율을 SQL로 집계할 수 있습니다.

**Q20. 인증이 없는데 운영에 쓸 수 있나요?**
아니요. 현재는 로컬 단일 사용자 데모이고 README와 API 설명에 명시했습니다. 감사 이벤트의 행위자도 `UNAUTHENTICATED_CLIENT`로만 기록해 "누가 했는지"를 주장하지 않습니다. 운영하려면 인증과 문서 소유자 기반 접근 제어가 먼저 필요합니다.
